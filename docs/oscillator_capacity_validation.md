# 振荡器实体数与时分复用容量验证

## 目标

本阶段验证两个参数独立的振荡器同时工作时，是否能支持：

- 8 个独立复音；
- 每个复音 `Unison=8`；
- 每个振荡器需要 `8 × 8 = 64` 个任务槽位；
- 一个振荡器使用 Acid 三维波表，另一个振荡器使用锯齿波，确认两路参数和波表访问彼此独立。

这里的“三维波表”是当前工程中的 16 帧 × 256 点 Acid 波表。`wt_position[6:3]` 选择相邻帧，`wt_position[2:0]` 做帧间线性插值；每个实体引擎各自例化一个双口同步 ROM 读取器。

## 调度预算

系统时钟为 50 MHz，内部采样率为 768 kHz。相邻内部采样请求间隔约为 65 或 66 个系统时钟。

一个实体引擎的流水线填满后每拍提交一个槽位，因此单引擎需要约：

```text
完成时间 ≈ SLOTS_PER_ENGINE + 流水线尾拍
```

测试使用 65 拍的紧预算。这样可以把“能完成”与“有足够时序余量”区分开：1×64 虽然能在 65 拍下完成，但在 64 拍压力下会置位 `schedule_overrun`，说明余量只有约 1 拍。

## RTL 仿真结果

测试平台：

- `sim/tb_dual_osc_capacity.v`：两个独立 Bank，64 个任务全部启用；
- `sim/tb_scheduler_unison8_capacity.v`：2×32 调度器，发送 8 个音符，每个音符 Unison=8；
- `sim/run_capacity_sweep.do`：比较 1×64、2×32、4×16、8×8。

### 65 拍预算

| 实体引擎 × 每实体槽位 | 总槽位 | 两路 Bank 输出 | 调度溢出 |
|---:|---:|---|---|
| 1 × 64 | 64 | 12/12 个样本有效 | 无，但余量很小 |
| 2 × 32 | 64 | 12/12 个样本有效 | 无 |
| 4 × 16 | 64 | 12/12 个样本有效 | 无 |
| 8 × 8 | 64 | 12/12 个样本有效 | 无 |

### 64 拍压力

`2×32`、`4×16` 和 `8×8` 仍然通过；`1×64` 产生 `schedule_overrun`。这说明 1×64 不适合作为保守的上板配置。

### 调度器验证

`tb_scheduler_unison8_capacity.v` 已通过：

```text
PASS: 2x32 scheduler allocates 8 notes at Unison=8 (64 tasks)
```

保守配置完成后，又用 `tb_dual_osc_capacity.v` 将参数改为 `VOICE_COUNT=64`、`UNISON_COUNT=1`，在 2×32 下占满 64 个任务槽位，12 个连续内部采样全部有效，两个独立 Bank 均无 `schedule_overrun`。因此当前架构的任务上限是每个振荡器 64 个活动任务：

```text
Unison=8：最多 8 个复音
Unison=1：最多 64 个复音
```

这两个上限共享同一组 64 个槽位；提高 Unison 会按比例减少可用复音数。

此前 `active_task_count` 只有 6 位，无法表示 64。现在已扩展为 7 位，并把 32～64 的倒数增益表补齐；64 个任务对应 `1/64 = 1024/65536`。

## 当前建议

推荐后续实际工程采用：

```verilog
OSC_ENGINE_COUNT = 2
SLOTS_PER_ENGINE = 32
```

理由是：

1. 满足双振荡器、8 复音、Unison=8 的 64 任务要求；
2. 每个实体只需处理 32 个槽位，远离 65 拍边界；
3. 相比 4×16、8×8，实体 ROM、包络状态寄存器和波表读取器数量更少；
4. 相比 1×64，布线拥塞和关键路径风险更低。

这只是 RTL 和综合前的容量结论。最终资源占用、最高频率和布线时间仍需用高云综合布线报告确认，尤其要检查 Acid ROM 是否按预期映射到 BSRAM。

## 2×32 高云综合布线结果

将工程默认参数设置为 `OSC_ENGINE_COUNT=2`、`SLOTS_PER_ENGINE=32` 后，用 GW5AST-138B、50 MHz 约束执行了完整综合布线：

| 指标 | 结果 |
|---|---:|
| Logic | 57,782 / 138,240（42%） |
| Register | 32,291 / 139,095（24%） |
| BSRAM | 41 / 340（13%） |
| DSP | 46 / 298（16%） |
| 布局布线耗时 | 21 分 1 秒 |
| PLL 生成时钟实际 Fmax | 45.120 MHz |

本次报告仍有 `PR1014`：`sys_clk_d` 使用了通用布线资源；生成时钟存在 1306 个 Setup 违例。它属于当前时钟树/约束问题，与 2×32 的任务调度容量是两个独立问题。容量验证已经通过，但正式提高系统时钟或上板前仍需继续处理该时钟违例。

## 完整顶层 MIDI 验证

新增 `sim/tb_top_dual_unison8.v`，直接例化当前 `top`，通过 UART 发送控制通道 CC 和演奏通道 Note On：

- OSC A、OSC B 同时启用；
- 两个振荡器的 Unison 都设置为 8；
- 依次发送 8 个音符，因此每个 Bank 都应分配 `8 × 8 = 64` 个活动任务；
- 检查两个 Bank 的采样有效脉冲同步、无调度溢出、UART 无帧错误。

测试命令：

```text
vsim -c -do "do sim/run_top_dual_unison8_test.do"
```

实测结果：

```text
PASS: top dual oscillator, 8 voices x Unison=8, 64 tasks per bank
```

这一项验证覆盖了从 MIDI 输入、控制参数路由、两个独立调度器，到两个 32 槽 TDM Bank 的完整路径。


## 2026-11-02：当前工程恢复为每路 2×32

`top` 默认参数调整为 `OSC_ENGINE_COUNT=2`、`SLOTS_PER_ENGINE=32`，OSC A 和 B 各自拥有 64 个任务槽位。每个实体仍每拍处理一个槽位；两个实体并行，各自处理32槽位，输出部分和在Bank内相加，并在归一化乘法前通过原有寄存器。保留原有时钟、采样率、波形、包络和调度结构，没有增加逐槽位运算的流水线级数。

注意：每增加实体引擎，就会复制振荡器核心、波表读取及外部双帧缓存；缓存加载仍通过广播同步到各实体。新增资源、布局拥塞及构建耗时必须以完整工程的新布局布线报告为准，不能从RTL仿真推断。上一份1×32基线是 `2b09db0`，Signoff总用时1334.2秒，`clk_sys` Fmax 50.490 MHz，系统时钟Setup违例端点0；DDR等路径仍存在报告违例。

### 本次仿真

- 当前默认参数的顶层 MIDI 测试：两路各8音符、Unison=8，共64任务，持续2000个输出采样无调度溢出；再设置短Release，释放并回收全部槽位，重新按键验证两路各分配8任务。仿真顶层使用FIR/PLL仿真桩，外部DDR波表关闭。
- Bank容量扫测：2×32下，64任务分别按8×8和64×1配置注入，65拍或64拍周期均得到12次有效采样，每路提交768槽位，无溢出。64×1是在Bank层直接写入槽位，不等于已通过64次MIDI按键顶层测试。
- 外部缓存广播：使用独立于音频时钟的加载时钟写入两帧常数，提交缓存后，检查A/B每个引擎都接收到预期插值6144，满64任务无溢出。此测试覆盖复制缓存的写入、同步及读取，不模拟DDR控制器、电气接口或SD装载链。
- 顶层双振荡器MIDI回归通过。未覆盖所有不相等Unison组合、拥塞下的完整DDR链及所有动态控制边界。

本次没有运行Gowin综合布线，也没有板测。后续以新报告核对系统时钟、DDR Setup/Hold、资源、各引擎波表RAM映射、Routing Phase 1及总用时，特别关注相较基线是否产生拥塞。确认这些结果后再判断此配置是否适合长期使用。
